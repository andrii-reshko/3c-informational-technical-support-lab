# Технічне завдання

## AI-система прогнозування навантаження на сервер (MVP)

# 1. Вступ

Цей документ описує вимоги до MVP системи прогнозування пікового навантаження на сервер із використанням нейронної
мережі (MLP) та інтервального прогнозу.

Система інтегрується з Prometheus, зберігає історичні дані у SQLite, виконує inference через модель, та надає REST
API і UI.

MVP охоплює лише **per-node прогнозування CPU та RAM** для **одного** горизонту (наприклад 15 хв).

# 2. Призначення

Система призначена для:

* прогнозування пікового навантаження CPU та RAM на окремий сервер;
* надання інтервального прогнозу (нижня та верхня межа);
* _сповіщення про прогнозовані піки (поза MVP)_

# 3. Терміни та визначення

**Node** - окремий сервер або інстанс, для якого збираються метрики та робиться прогноз.

**Horizon** - часовий інтервал у майбутньому, на який робиться прогноз (5/15/60 хв).  

**Peak** - максимальне значення ресурсу (CPU або RAM) у заданому горизонті.  

**Interval prediction** - прогноз у вигляді нижньої та верхньої межі (наприклад 10-90% квантилі).  

**Feature / Feature vector** - набір числових характеристик, який подається на вхід моделі.  

**Lag feature** - попереднє значення ресурсу, що використовується для прогнозу.  

**Rolling statistic** - середнє або максимум за останнє N хв для згладжування тренду.  

**MLP (Multi-Layer Perceptron)** - повнозвʼязна нейронна мережа для прогнозу на основі фіч-векторів.  

**LSTM (Long Short-Term Memory)** - Це нейронна мережа зі спеціальною пам’яттю, яка розуміє послідовності.  

**TFLite** - легка версія моделі TensorFlow для швидкого inference у сервісі.  

**Predicted peak** - очікуваний максимальний ресурс на обраному горизонті.  

**Lower / upper bound** - нижня та верхня межа інтервального прогнозу.  

**Headroom** - запас доступного ресурсу до максимальної потужності сервера.  

**Quality metrics** - показники точності моделі (MAE, RMSE, coverage).  

**Hardware profile** - конфігурація серверного заліза (CPU cores, RAM).  

**Collector** - сервіс збору метрик з Prometheus та запису у БД.  

**Inference service** - сервіс прогнозування на основі моделі та останніх даних.  

**Training pipeline** - процес підготовки даних, навчання та збереження моделей.  

**Forecast** - інтервальний прогноз ресурсу для конкретного вузла та горизонту.  

**Artifact / model artifact** - збережена модель з мета-даними і scaler.  

**Scaler (нормалізатор)** - інструмент, який перетворює числа у зручний для моделі діапазон.

# 4. Загальний опис

## 4.1 Архітектура системи

Компоненти MVP:
* Prometheus - джерело метрик
* Collector на Go - збір і запис у БД
* Inference service, REST API, UI на Go
* SQLite для зберігання метрик
* Training pipeline на Python для навчання моделей та збереження артефактів

## 4.2 Основна функціональність

### 4.2.1. Збір метрик

Collector у заданий інтервал 5 секунд отримує CPU usage, RAM usage, timestamp, записує у БД.
У штатному режимі збирає метрики на льоту. При запуску або перебої використовує backfill для заповнення пропущених даних.

### 4.2.2. Зберігання даних

Зберігаються, історичні метрики, прогнози, hardware profile, (можливо дані для версіонування моделей). 
У БД зберігаються метрики за останні 7 днів, старіші видаляються.

### 4.2.3. Побудова датасету

Формуються:
* лаг-фічі (t-1..t-30)
* rolling mean
* rolling max
* час доби
* день тижня

Target:
* max(resource) у наступні N хв

де resource – CPU або RAM, N – горизонт прогнозу у хвилинах.

### 4.2.4. Модель

* MLP (примітка: MLP простіше дебажити, швидше тренується, а LSTM має сенс, якщо дуже довгі сезонності, складні патерни, багато шуму, в рамках MVP не реалізовуємо)
* окрема модель для CPU та RAM
* окрема модель для кожного горизонту (в рамках MVP обмежимося одним горизонтом, наприклад 15 хв)
* quantile regression – спосіб навчити модель прогнозувати не одне число, а діапазон можливих значень (0.1 та 0.9)

### 4.2.5. Inference

По заданому інтервалу (наприклад кожну хвилину) формується фіч-вектор, викликається TFLite.
Інтервальний прогноз у MVP не зберігається, а повертається одразу через API.

# 5. Use Cases

## 5.1 Підключення Prometheus

Адміністратор задає URL та credentials (опціонально) для підключення до Prometheus по HTTP API. Collector перевіряє зʼєднання та починає збір метрик.

## 5.2: Реєстрація Node

Автоматично реєструється при отриманні метрик від Collector. Адміністратор може відредагувати апаратний профіль (CPU cores, RAM) для кожного вузла через UI.

## 5.3: Збір метрик

Collector автоматично зберігає метрики кожні 5 секунд.

## 5.4: Навчання моделі

Пайплайн навчання
* формує датасет
* навчає MLP
* зберігає TFLite, Scaler, та мета-дані про модель (версія, дата, метрики якості)

## 5.5: Отримання прогнозу

API повертає
* lower
* upper
* horizon

## 5.6: Перегляд у UI

Користувач бачить
* поточне навантаження
* прогноз на N хв
* індикатор ризику піку
* графік історії + інтервал

# 7. User Interface (Інтерфейс користувача)

## Dashboard
* Відображення списку вузлів (nodes) у вигляді карток.
* Вузли додаються автоматично при отриманні метрик від Collector.
* Кожна картка показує:
  - Заголовок: назва вузла та бейдж ризику (safe | warning | critical)
  - Поточне навантаження на CPU (%)
  - Поточне навантаження на RAM (%)
  - Спрощений графік: за останню годину і горизонт прогнозу (наприклад 15 хв).
  - Прогнозні піки.
* При натисканні – перехід до детального перегляду вузла.

## Node Details
* Навігація: кнопка "Back to dashboard" для повернення до списку вузлів.
* Назва вузла.
* Індикатор ризику: кольоровий бейдж, який змінюється залежно від прогнозу (зелений - безпечний, жовтий - попередження, червоний - критично).
* Апаратний профіль: CPU, RAM, Safe operating boundary (граничні значення для ризику).
* Поточне навантаження: відображення поточного використання CPU та RAM у відсотках.
* Графік – показує використання конкретного ресурсу за останню годину, поточний показник, та інтервальний прогноз на наступні 15 хвилин. 
  На графіку також відображаються горизонтальні лінії, які позначають пороги ризику.
* Quality metrics (метрики, що показують, як модель прогнозує, для оцінки довіри до прогнозу):
  - MAE (Mean Absolute Error) – середня абсолютна помилка між прогнозованими та фактичними значеннями.
  - Coverage – відсоток випадків, коли реальне значення потрапило всередину прогнозованого інтервалу $[q_{0.1}, q_{0.9}]$. Якщо Coverage < 80%, моделі не можна довіряти.

## Hardware Profile

Поля: CPU cores, RAM (GB), Safe operating boundary
Система показує: прогноз у %, прогноз в абсолютних значеннях (cores, GB), запас потужності

# 9. Вимоги до зовнішніх інтерфейсів

## 9.1 Інтерфейси додатку (REST API)

### Nodes

| Протокол | Метод | Endpoint                    | Опис                                                                |
|----------|-------|-----------------------------|---------------------------------------------------------------------|
| http/wss | GET   | /nodes                      | Список вузлів з поточними метриками та прогнозами                   |
| http/wss | PUT   | /nodes/{node_id}            | Оновлення апаратного профілю вузла                                  |
| http     | PUT   | /nodes/{node_id}/visibility | Управління видимістю вузла на дашборді (наприклад, приховати вузол) |

### Metrics

| Протокол | Метод | Endpoint                 | Опис                                                  |
|----------|-------|--------------------------|-------------------------------------------------------|
| http/wss | GET   | /nodes/{node_id}/metrics | Історія метрик для вузла (CPU, RAM) за останні 7 днів |
